# Cloudflare 远端维护

备份目标的「远端维护」提供版本清理和设备接管。先用 `pnpm run cloud:deploy` 升级 Worker，并应用全部 D1 迁移（包括 G10 新增的 `0006.sql`）；Wrangler 管理的地址和 Token 继续自动取得。

## 版本保留与清理

默认保留当前 lineage 最近 30 个已提交版本，可以调整数量。先「预览清理」，核对待删除版本 UUID、无引用对象数量与预计字节数，再勾选永久删除确认。预览不删除数据，有效期 10 分钟；版本、上传或恢复保护发生变化时，需要重新预览。

清理只移除所选分支的旧版本。所有分支的 head、其他分支已提交版本、仍有效的 staging manifest 和有效恢复 pin 均参与保护。每个保留版本有完整 checkpoint，因此恢复不依赖被删除的旧 delta。对象按全部受保护 manifest 的引用标记，且 R2 上传时间必须已超过 24 小时，才成为回收候选。恢复开始时取得一小时 pin，每 30 秒续期，结束后释放。

确认执行后，在 D1 中锁住整个远端 Notebook，阻止新上传计划、提交、接管和新增恢复 pin。已持有的恢复 pin 可继续续期。待删除版本先标记为 retired，不再对外列举或恢复；随后分批删除 R2 对象、旧 manifest 和对应 D1 数据。每次最多处理 8 个对象或 8 个版本，使用持久化游标及执行锁，避免并发重试倒退进度。全部完成后释放 Notebook 锁；已完成计划可重复确认。

普通网络或删除失败会保留清理计划与 Notebook 锁。配置了持久化协调器的新 Worker 会通过闹钟恢复已经确认的计划，并在新协调器实例创建后安全释放旧实例的单批执行锁；不通过时间过期抢占活跃删除。旧版遗留且没有协调器身份的执行锁仍需管理员确认旧请求停止后处置，见「旧维护锁处置」；不会按时间抢占，也不会直接清除 Notebook 锁。升级包括 `0003.sql` 和 Durable Object 绑定，详见 [P0 备份可靠性](../development/validation/P0-BACKUP-READINESS.md)。

规划预算：整个 Notebook 最多 2000 个活动版本（包括 staging），新版本入场在事务内检查预算；达到上限仍可预览并清理。保留数可设置为 1–1000，日/周/月采样上限分别为 365 天、104 周和 120 月。所有保留版本的引用最多 200000 个；`objects/`、`manifests/`、`staging/` 各最多扫描 10000 项，每个计划合计最多回收 1000 个对象，超出候选留待下次预览。超出扫描/引用预算、保护身份缺失或保护 manifest 缺失/损坏时拒绝规划，不删除任何备份。云端运行时配额可能先于应用预算触发；满预算真实负载交 G07 验收。

## 维护记录生命周期

`maintenance-lifecycle-v1` 和 `0005.sql` 定义以下契约。版本和对象删除始终需要手动预览与确认；保存配置不触发删除。

| 记录                                 | 保护与回收规则                                                                                                                                                                                                 | 恢复/重试证据                                                                                          |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| staging generation                   | 以服务端 `generation_activity.touched_at` 计时；plan 重试、对象及 multipart 请求刷新活动并增加 revision。当前分支连续 7 天无活动后可列入清理；其他分支 staging、head 和有效 pin 仍保护。缺少活动记录时保守保留 | 确认时复核保护与 revision；先 retired，再删 manifest/D1；迟到的 commit 必须仍能在事务内找到 staging 行 |
| 孤立 manifest / 已完成的上传临时对象 | manifest 无活动 generation；临时对象无活动 generation、所属版本已 committed，或版本已被本次列为删除；R2 年龄至少 24h 后进入候选                                                                                | 固定预览基准、ETag 复核、持久化对象游标；并发入场通过 maintenance epoch 与维护锁阻断                   |
| 未确认清理计划                       | 有效期 10 分钟；最多 128 个有效预览。后续预览分批归档已过期计划，每次最多 64 个                                                                                                                                | R2 保留原计划，过期计划不能重新执行；归档删除用 status 条件保护正在执行的计划                          |
| 已确认计划                           | 不按时间过期；失败保持 Notebook 锁，由协调器恢复。完成后在后续手动清理中归档                                                                                                                                   | 完整计划与游标写入 R2 后才删 D1；归档后的 completed 计划重复确认仍返回完成                             |
| 接管回执                             | 当前 epoch 的回执保留 D1；更旧 epoch 在手动清理中归档                                                                                                                                                          | 重试检查原始请求字段与当前 writer/epoch；旧回执不能重新夺回写入权                                      |
| retired 墓碑                         | 对应 generation 已删除后归档，归档成功才删 D1                                                                                                                                                                  | 上传 plan 同时检查 D1 与 R2 墓碑；入场 maintenance epoch CAS 防止跨归档窗口复活旧 ID                   |

归档键为 `maintenance/<Notebook>/<plans|claims|retired>/<UUID>.json`。每个确认执行批次最多归档每类 64 条；归档失败保留锁和原记录，重复写入/删除可续跑。活动计划与执行锁不归档，历史记录不计入 2000 个活动身份预算。过期恢复 pin 在持锁维护中删除。

R2 归档长期保留，不设置自动销毁期限，否则无法永久拒绝旧 UUID 重放或核对历史清理。因此 D1 工作集可回收，R2 证据仍随历史增长；真实归档成本和长期负载由 G07 测量。`transfer-resume-v1` / `0006.sql` 将传输及服务端复制会话登记到 D1，每 Notebook 最多 2000 条。所属版本被本次选为删除时，或版本已提交/不存在且登记满 24h 时，会话进入手动预览；其他分支活动 staging 继续保护。会话与对象共用每计划 1000 项、每批 8 项预算，先 abort 再删登记，失败保留维护锁和游标，重试不会删除同名已发布对象。预览单独展示本批会话数，未完成片段的字节数仍不计入空间估算。R2 创建与 D1 登记之间的空会话窗口依靠桶未完成 multipart 生命周期兜底；部署应保留该规则。详见 [ADR-014](../design/adr/014-cloudflare-transfer-resume.md)。

## 按目标保存与空间预估

先调整数量和采样窗口并预览，展示当前数据占用、本批预计释放、清理后预计占用，以及需要后续预览的候选数；再点「保存保留配置」。配置持久化在本机目标记录中，重启后按目标读取，不跨目标共享。仅预览不会覆盖已保存配置；保存也不会确认计划或启用自动备份/自动清理。

空间依据 R2 实际对象大小去重统计，包括数据库块、附件、manifest 和已完成的上传临时对象；本批释放量包括待删版本 manifest。受 24h 宽限期或 1000 项候选上限限制而留下的对象仍计入预计占用。维护归档、D1、未完成 multipart 分段及服务商计费不在估算内，不能把预估当账单。首次无历史版本时需先完成一次备份，才能为该分支生成预览。

## UTC 日/周/月采样

在最近 N 个版本之外，可叠加「每日采样保留天数」「每周采样保留周数」「每月采样保留月数」。每个 UTC 日、周、月窗口保留其中最新的一个已提交版本；周从周一开始，窗口包含当前时间段。三项默认 0，即关闭采样，沿用原来的最近 30 个版本策略。

例如最近 1 个版本 + 7 天日采样 + 4 周周采样 + 12 月月采样，会保留各窗口代表版本的并集，同一个版本满足多个规则时只保留一次。采样只增加保护，不降低其他分支、head、staging 和恢复 pin 的保护。预览中可展开「查看策略保留版本与原因」，核对最近版本、日/周/月采样及未来时间保护。

时间来自版本 checkpoint 的 `createdAt`，解析为绝对 UTC 时间；不是 R2 对象上传时间。预览记录固定的 UTC 基准，确认时复用，跨午夜、周一或月初仍按原计划判断。未来时间版本保守保留，时间格式无效则拒绝规划。设备时钟错误会影响采样分桶，需要核对预览；不会据此自动修正云端历史。

采样仍为手动预览/确认流程，不自动定时删除；数量和窗口可按目标持久化，手动预览优先使用已保存值。旧版仅按数量生成的未完成计划继续兼容；新客户端遇到不支持 `calendar-retention` 的 Worker 时，拒绝非零采样请求，提示升级，不悄悄退回数量策略。

## 设备接管

填写已有远端 Notebook UUID 和 lineage UUID，读取当前 head、writer epoch 和设备 UUID，再明确确认接管。服务端按 head 和 epoch 做条件更新，递增 epoch 并记录幂等回执。旧 epoch 的上传与提交会被拒绝，旧设备仍可读取。

本地恢复副本拥有新 Notebook UUID。接管时保存独立的 `remoteNotebookId`，继续指向原远端分支；上传副本会重建远端 Notebook 身份和已知的自指笔记链接，不改写本地源库。接管不会合并两端内容，自动备份会关闭，并清空旧 ack 与 pending 状态。先核对本地内容，再手动备份；后续可自行开启自动备份。

APP_TOKEN 是整个个人服务的授权凭据。设备 UUID/epoch 用于并发写入控制，不是独立设备身份认证或多用户权限系统。

## 旧维护锁处置

协调器只会清除带协调器身份的执行锁。旧版 Worker 在 `/retention/apply` 中写入的 `execution_id` 没有 `execution_owner`，这类无主执行锁被保守保留，不会自动过期；`maintenance-recovery-v1` 解决的是协调器实例被回收后留下的执行锁，不覆盖这种旧锁。

先做只读诊断，确认是否存在无主执行锁与 Notebook 锁：

```sh
pnpm run cloud:legacy-lock <远端NotebookUUID>
```

返回 `notebookLocked`、`legacyLock`，以及活动计划的 `executionId`/`executionOwner`/游标。诊断不改变锁状态。确认旧请求已停止后，用同一命令释放被观测到的确切执行锁：

```sh
pnpm run cloud:legacy-lock <远端NotebookUUID> --release <计划UUID> <执行UUID> --confirm-legacy-stopped
```

释放要求显式确认与「旧请求已停止」声明，并且只清除与诊断中 `planId`、`executionId` 完全一致、`status='deleting'`、`execution_owner IS NULL` 且归属同一 Notebook 的执行锁；条件不满足返回 `LEGACY_LOCK_CHANGED`，不会误清其他锁，也不会触碰协调器持有的执行锁。释放后 Notebook 锁继续保留，并写入 `maintenance_admin_actions` 审计记录；随后在维护界面重试未完成的清理，由协调器从持久化游标续跑同一计划。

必须先证明旧请求已停止，例如部署新 Worker 并确认旧版本不再有 `/retention/apply` 活动；不能按锁的时间长短猜测其是否仍在运行。`/v1/capabilities` 公布 `maintenance-admin-v1`，`0004.sql` 建立审计表。
