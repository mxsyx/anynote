# G08 本地备份规模与响应验证

日期：2026-10-21。基线提交 `c1ad96e`，优化为同工作区未提交改动；本组已完成并移出待办，实施交接见 [历史记录](todo-2026-10-24.md#g08)。

## 范围与契约

实现范围包括本地备份引擎、共享数据库捕获、资源闭包扫描、任务查询/取消和规模脚本。保留写队列捕获切点、不可变附件固定、根身份及符号链接检查、复制写后哈希、原子清单发布、旧副本保护及失败时等待所有 worker 的约束。跨会话免捕获没有纳入本次实现。

- 闭包使用 SQLite 迭代器，每 256 项让出事件循环，避免 `.all()` 再投影的临时数组；本地捕获去除已经在 snapshotDatabase 完成的重复闭包检查。
- 元数据检查与附件固定有界并发，复用旧清单；扫描、复制与完整校验共享进程内 4 个 I/O 槽。目标复制并发配置仍生效，同目标范围任务仍串行。
- 清单逐批校验、约 64KiB 分批序列化；成功发布后不重复解析 pending、不重写空 cleanup。十万附件与数据库块使用一致的文件/日志上限，完整替换所需 JSON 读取预算为 128MiB。
- 小文件复制与哈希缓冲按实际大小分配，上限仍为 1MiB；避免十万份 1KiB 文件反复分配 MiB 级缓冲。
- `listTasks` / `cancelTask` 不再等待捕获写队列；取消传递到 SQLite 备份回调、扫描与附件固定。暂存清理异步执行，结束后才公开任务终态。

捕获 barrier 仍覆盖附件固定。提前释放它需要独立的资源生命周期契约，本次没有将仅改善控制响应解释为编辑写入无需等待捕获。同步 SQLite 完整性查询和 JSON 解析仍可能产生短暂停顿。

## 环境与复现

本机 Apple M4 / 32GiB / macOS 26.2 / APFS，同盘源和目标、热缓存、单次阶段测量。基准进程为 Electron 内嵌 Node 24.17.0；桌面为 Electron 41.9.1 / Chromium 146。完整回归使用原生 Node 24.22.0。

Node 语料为 10,000 / 100,000 个附件、约 100MiB SQLite：大多数附件 1KiB，含 8 个 8MiB 合成 PDF，另加 1GiB 流式取消样本。桌面语料为确定性 `g08-asset-N` 的 1KiB 文件、约 100MiB SQLite 和第二个 Notebook。两种语料不同，只分别做前后比较。基准准备直接生成测试附件和数据库记录，排除准备耗时；生产附件入库仍由独立存储回归覆盖。

```sh
pnpm run benchmark:local-backup --samples 10000:100,100000:100 --report-path artifacts/g08-node-final.json
pnpm run test:desktop:local-backup --scale --samples 10000,100000 --report-path artifacts/g08-electron-final.json
pnpm run test:desktop:local-backup --report-path artifacts/g08-desktop-acceptance.json
pnpm exec vitest run tests/backup-local.test.mjs
pnpm run typecheck
```

桌面规模脚本每阶段默认超时 2 小时，可用 `--timeout-ms` 调整；失败保留隔离夹具，并支持 `--reuse-root` 经正常 pending 恢复后续跑。复用夹具的首次阶段含恢复成本，单独标记，不能当作全新首次复制耗时。

原始 JSON / 日志位于被 git 忽略的 `artifacts/`，不作为已提交仓库附件。长任务期间有其他本机测试/数据准备并行，首次复制墙钟耗时会受到竞争影响；不能从单次墙钟变化宣称 SSD 吞吐提升。帧统计来自真实 renderer，查询经过真实 IPC；按阶段分类使用最后观察到的阶段，Node 的 `phaseWallMs` 按引擎进度划分；`cancel-large-file` 最后一个复制阶段标签包含随后执行的旧副本复验，不能将它当作纯复制耗时。

## 规模测量

### 原版边界

`artifacts/g08-node-before.json`：10,000 附件六阶段通过；100,000 附件在首次计划阶段真实触发 `files` 数组 100,000 上限并失败。附件上限没有为数据库块留空间，旧 pending 上限也仅为 20,480。本次统一为 120,480；原版无法提供成功的十万附件零变化/提交基线，不能拿旧格式 Linux 的“30 秒 / 825MiB”充当本机前值。

这说明 renderer 和控制通道可以在捕获/提交期间继续工作，但并非所有后端操作都已无停顿：十万清单的同步 JSON 解析、SQLite 查询仍有约 1 秒量级等待，峰值内存也仍随清单规模增长。捕获 barrier 内的普通写入仍会等待。

中间脚本曾误用完整校验更新前的时间戳比较取消清单，已改为比较取消前最新清单；还出现过 Electron 启动超时、临时目录复用/清理冲突及过短的 20 分钟阶段上限。最终运行采用保留隔离夹具、正常恢复与 2 小时阶段上限；上述中间失败不计入通过证据。

边界：合成语料不替代真实用户内容分布；没有测低配置机器、外接 USB/HDD、冷缓存、拔盘或断电。其他设备测量归属 G03/G04，当前实现不等待这些样本。
