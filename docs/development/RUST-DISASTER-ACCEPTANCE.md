# Rust 物理盘与灾难恢复验收（RM33）

本文维护 Rust 接口、约束和验证方法；未完成工作统一见 [TODO](TODO.md)。

## 本机预验证

需要 Python 3.11+、仓库锁定 Rust 工具链及本平台依赖。无 Pdfium、GUI 或 Node 前置，使用合成资料：

```sh
python3 scripts/rust-disaster-batch.py --device mac-arm64-lab --strict
```

产物写到新建的 `tmp/rm33/<UTC时间>-<pid>/`。批次复用 RM32 的源码摘要及 RM31 的进程管理/超时/非空测试检查，串行运行：

1. 恢复证据校验测试；本平台硬件/物理盘信息采集（当前仅 Mac 有系统补充采集）。
2. `local_backup`、`archive`、`migration` 既有 Rust 测试，不以模拟卷、故障返回或进程退出替代实物故障。
3. 构建 `local_backup_probe` 和 `archive_probe`，从 Cargo 实际输出定位可执行文件并记录 SHA-256。
4. 调用产品同一 `NativeVolumes` 检查测试目录。`--inspect-path <现有目录>` 可重复指定额外只读探测路径；不在这些路径执行备份或故障操作。Mac 另保存 `diskutil info`，物理映射需人工核对，不能把 `deviceId` 或 UUID 差异当作独立物理盘证据。
5. 准备便携包，删除准备阶段的合成源副本，然后在新目录恢复两种格式并逐项核对。

`report.json` 记录设备标签、平台、源码/Cargo.lock/二进制摘要、原生卷事实、每阶段命令/日志/结果、恢复核对和源码在批次内是否变化；`source.json` 保存逐文件摘要。测试集合为空、非零退出、崩溃、超时、源码变化或缺少恢复结果都不通过。`acceptance` 始终为 `incomplete`，实物、远端、回退和最终包字段均不自动放行。检查失败退出 1；全部预验证通过时 `--strict` 退出 2，不加 strict 退出 0 也不代表 RM33 完成。

这批脚本在 Windows/Linux 的实际运行尚未验证；它们会使用本平台 Rust 卷 API，但硬件/物理拓扑记录仍需补齐。不能把重新构建的 debug 驱动标为最终安装包验收。

## 双格式便携恢复

```sh
cargo build --locked --offline -p anynote-services --example local_backup_probe --example archive_probe
python3 scripts/rust-recovery.py prepare tmp/rm33-transfer --device source-lab
# 将输出的 Manifest SHA-256 单独保存，随证据记录交给接收设备。
# 把整个 bundle 复制到另一台设备；接收端使用相同源码/锁文件构建本平台驱动。
python3 scripts/rust-recovery.py verify tmp/rm33-transfer --output tmp/rm33-received --device destination-lab --expected-manifest-sha256 <源端记录的摘要>
```

目标平台可用 `--binary`、`--archive-binary` 指定驱动；Windows 默认包含 `.exe` 后缀。驱动依赖安装和工具链是测试工具前置，不能据此声称最终产品无需开发环境即可恢复。

包中包含 `disk/` v3 本地副本、`full.anynote` 完整归档、`expected.json` 源端逻辑预期和 `bundle-manifest.json` 全文件大小/SHA-256。准备完成才写 manifest；中途失败的目录保留用于诊断，不能作为完成包，重试须指定新目录。旧 RM31 包没有完整归档与新 manifest，须重新 prepare，不提供历史测试包兼容分支。

验证在启动恢复前检查摘要、必需载荷和文件集合，拒绝新增/丢失/修改文件、符号链接和非普通文件。源端单独记录的 manifest 摘要用于跨设备核对；未传 `--expected-manifest-sha256` 只证明包内自洽，报告的 `manifest_pinned=false`，不证明来源真实性。摘要不是签名。恢复目的地必须全新且与 bundle 无交叠。

两条恢复分别保存结果和耗时，即使一条失败也继续收集另一条结果。共同核对 SQLite integrity/外键、12 张业务表、全部登记资源的大小/hash、历史和回收站、批注、`extension_data`、采集/导入回执、自链接和 FTS 查询；新库身份必须改变。完整归档按现有 Full 契约仅裁剪无引用 asset；本地 v3 保留全部 asset。比较不会丢弃未知 JSON，也不通过恢复后的结果生成预期。哈希以流式读取完成，Python `-O` 不会禁用验收检查。

本地 verify 会更新 `lastFullVerifiedAt`，因此只操作 bundle 的私有复制；归档只读。验证结束再次检查整个传输包未变。输出 `recovery-report.json` 包含两端设备标签/主机/平台/时间、两端驱动摘要、manifest 摘要及每格式业务结果。设备名不同不证明物理独立，`physical_device_independence=not_proven` 始终需要真人设备记录补证。

本驱动使用小型黄金语料，不能覆盖全部媒体或大数据性能。当前便携语料的 `note_text` 为零行，FTS 只查询固定 `Markdown` 词；不能把它当作 PDF 全文/所有语言搜索验收。远端 committed 版本、系统配置/凭据和最新数据回退不在便携包中，必须按下面清单单独完成。

## 真实设备批次执行清单

每条记录：操作者/时间、源端与恢复端物理设备标签、OS/架构、文件系统与稳定卷身份、分区到物理盘映射、候选包与资料摘要、数据量/最大附件、缓存条件、实际步骤/切点、预期/实际结果、日志及外部观察证据、状态（passed/failed/blocked/not_tested）。不要记录凭据明文。每组只操作已指定的独立测试资料和测试盘；同盘串行。

| 条目                      | 必做操作与判据                                                                                                                                                                      | 当前缺口                                                                                                                                                      |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RM33.1 身份/拓扑，V008    | APFS/NTFS/ext4/exFAT 各自保存 OS 原始信息与 Rust 输出；同盘两分区、两块独立盘、未知/虚拟盘分别核对提示；重启和重连后核对稳定卷身份                                                  | 本轮只有内置 APFS 的一次探测；物理设备映射/UI 完整实现仍归 F002，不在批次脚本伪造                                                                             |
| RM33.1 路径/限制，V009    | Windows 真 NTFS 对文件持有不允许替换的真实句柄，验证替换失败/有限重试；长路径及源目标交叠不得误发布；真实网络盘拒绝；FAT32 对超过 4 GiB−1 的完整附件/恢复 DB 拒绝                   | 当前只有 fixture；FAT32 不是无条件拒绝小文件，沿用已有单文件预算契约                                                                                          |
| RM33.1 性能，V008         | SSD→SSD、SSD→HDD、USB；分别记录冷缓存/首用/连续运行、实际字节和耗时、吞吐/RSS、旧版同机对照，按既有预算判定                                                                         | 小型同机恢复耗时不构成性能验收                                                                                                                                |

实物记录完成后，在 `docs/development/validation/` 建立对应设备报告并更新[开发索引](README.md)；日志/照片可先放 tmp，但验收结论、失败归属和资料的持久保存位置须写入报告。各平台和盘组合独立判定，不以本机 APFS 结果关闭 NTFS/exFAT/ext4 或不同物理盘条目。
