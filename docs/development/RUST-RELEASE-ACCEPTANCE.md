## 生成和复核证据包

```sh
python3 scripts/rust-release-acceptance.py init --output tmp/rm38/batch/evidence.json
python3 scripts/rust-release-acceptance.py check \
  --evidence tmp/rm38/batch/evidence.json --output tmp/rm38/batch/review.json
```

输出文件必须尚不存在。退出码：`0` 表示模板生成成功或证据完整可供人工复核，`2` 表示缺证/前置未闭合，`1` 表示输入格式或 I/O 错误。模板的成功退出不表示检查成功。报告始终 `publication_authorized: false`；最好的状态只是 `ready-for-review`，不是已实测、已放行或已授权发布。

`candidates` 填入证据包目录内的相对 `candidate.json` 路径；每个候选旁必须有原始 manifest 和原始安装器。检查器核对：四架构各一份、相同干净 commit/tree/Cargo.lock、release profile、应用身份/schema/版本、CI run/attempt/提交/runner 架构、资源自检、安装器和 manifest 的 SHA-256/长度，以及 macOS app/安装器两个 Accepted 公证请求 ID。旧报告缺字段、unsigned、重复目标、混用提交和篡改文件都会阻止复核。

构建在开始和结束采集 Git 身份。`source_unchanged` 仅在两次一致且均干净时为 true；Cargo.lock 摘要取提交中的规范内容，避免跨平台换行差异。CI 字段仅采集公开运行标识，不包含 secrets；公证只保存请求 ID 和状态。候选来源字段不是签名证明，设备侧仍须独立核验发布者、信任链、时间戳、公证票据和安装器内容。

每个 `records` 条目的 `status` 默认 `not-run`。实际执行后使用 `passed` / `failed` / `blocked`，填写未执行或失败原因；仅允许上述明确的远期/取消项为 `deferred`。通过或延期条目的 `evidence` 为非空数组，每条包含：

| 字段                      | 要求                                                                                   |
| ------------------------- | -------------------------------------------------------------------------------------- |
| `file`、`sha256`          | 证据包内非空原始报告/脱敏日志的相对路径与 SHA-256，不接受越界路径或符号链接            |
| `version`、`commit`       | 与本次候选相同，禁止把旧报告改字段当重测                                               |
| `candidate_sha256`        | 原始 `candidate.json` 文件摘要数组；平台条目绑定该平台一个候选，跨平台汇总绑定全部四个 |
| `device`                  | 非敏感设备代号、系统/架构及必要环境；聚合报告注明所含设备                              |
| `corpus`                  | 实际样本标识、规模、内容摘要/版本与克隆来源，不写用户私密内容                          |
| `command`、`result`       | 实际命令或 GUI 操作步骤、退出码及逐场景观察；不能只写“测试通过”                        |
| `recorded_at`、`reviewer` | 带时区的 ISO 时间和复核人；延期必须附实际范围决策和原因                                |

检查器核验文件完整性和关联关系，**不判断任意日志文字是否真的证明业务通过，也不能认证手填的 reviewer、CI 地址或签名声明**。负责人须核对原始 CI 页面、平台工具输出和实物操作。测试 fixture 不可进入实际证据包。清理 `tmp/` 前，将真实证据归档到受控长期位置，并在本文件保留版本/摘要/归档定位和结论；本轮没有可归档的真实终验证据。

## RM38.1：同一候选的实际执行顺序

1. 先闭合 RM37 的功能与退役前置，确认 F007 范围。使用包含完整源码、锁文件和发行脚本的干净提交；修复后必须生成新候选并复验受影响项，不能沿用旧哈希。确认 A011 的真实身份和 CI environment；凭据预检仅检查配置。
2. 在该提交运行 `Native desktop candidates`，手动 `sign=true`，等待 Rust 与保留 TS workflow 及各架构打包全部完成。记录 run URL、attempt、commit、runner；下载原始安装器、candidate、manifest、payload-tests 与 SHA256SUMS。Linux 当前签名未启用，不能由 `sign=true` 或校验和推断其已实签；先补齐经 F007 确认的策略。
3. 在对应干净设备验证安装器摘要和实际签名。macOS 保留 `codesign --verify --deep --strict`、预期 Team ID、Developer ID 证书信息、`spctl --assess`、app/DMG 的 `xcrun stapler validate` 及公证请求结果；Windows 保留 `signtool verify /pa /all /v`、Get-AuthenticodeSignature 的签名者指纹与时间戳。验证命令非零立即停止安装，保存脱敏输出。
4. 从**下载的安装器**安装，记录设备、目标路径、安装器和运行程序版本/架构，不以源码目录或 `--release-check` 代替 GUI 首启。预装依赖按 [安装要求](../features/NATIVE-INSTALL.md)记录；断开网络、清除开发 Pdfium 环境变量、使用隔离账户/测试库，完成笔记编辑保存重启、白板、图片、PDF、导入/备份等首用检查。在线视频/云操作记录为联网能力，不能编造离线成功。
5. 在同设备以已记录的前一版本、隔离测试库执行升级；记录升级前后正文/历史/资源/批注/未知状态/配置及外部登记。失败演练覆盖错误架构/身份、篡改资源、不支持 schema、占用文件、切换前和切换后失败，核对程序回退和数据不丢失。既有 `test-native-payload.py` 只覆盖目录回归，不能替代 DMG 拖放、NSIS 或 AppImage 的真实路径。
6. 卸载后核对用户数据和外部 Notebook 的完整性，重新安装并读回。保留 `.previous`、失败目录和安装日志；任何目录锁、恢复重命名失败都先调查，不能删除锁重试假装恢复完成。对四目标分别填写证据，不把本机结果复制到未测设备。
